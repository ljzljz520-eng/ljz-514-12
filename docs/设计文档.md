# 设计文档（中文）

## 1. 设计目标
- 提供清晰、可用的线路规划交互：选起点/终点 → 一键规划 → 地图与列表同步展示
- 算法与数据解耦：支持从 `edges.csv` 明确定义道路/连接关系，也支持按经纬度自动生成边作为兜底
- 可部署、可复现：`docker compose up -d --build` 一键运行

## 2. API 设计

### 2.1 健康检查
- `GET /api/health`
- 返回：`{ status: "ok", time: "..." }`

### 2.2 节点列表
- `GET /api/nodes`
- 返回：节点数组 `[{ id, name, lat, lng, type?, desc? }, ...]`

### 2.3 最短路径
- `GET /api/path?from=<id>&to=<id>`
- 成功返回：
  - `startId` / `endId`
  - `totalDistanceMeters`
  - `pathNodeIds` / `pathNodes`
  - `segmentDistanceMeters`
- 失败返回：`{ error: "...中文错误信息..." }`

## 3. 前端交互设计

### 3.1 控制面板
- 起点/终点下拉选择（支持搜索）
- 交换起终点、清空选择
- 一键规划并展示：综合耗时、纯步行耗时、总距离、换乘次数、最大坡度、平均拥挤等汇总指标
- 路径节点列表中，每两个景点之间展示该段明细（步行耗时、距离、坡度、拥挤程度、是否需换乘）
- “为什么推荐这条路？”：与备选路线逐项对比，自动说明推荐路线的优势与备选路线的取舍

### 3.2 地图交互
- 渲染所有景点 Marker
- Marker Popup 支持“一键设为起点/终点”
- 规划成功后绘制路线 Polyline：按路段拥挤程度着色（绿=清净、黄=一般、红=拥挤），需换乘路段以虚线表示，并附图例

## 4. 数据与容错设计

### 4.1 CSV 数据
- `nodes.csv`：必须存在且包含列 `id,name,lat,lng`（其他列可选）
- `edges.csv`：可选；至少包含 `from,to`；每条连接记录真实路况属性：
  - `distance_meters`：实际步行距离（米，非直线距离）
  - `walk_minutes`：步行耗时（分钟）
  - `slope_percent`：平均坡度（%）
  - `transfers`：通过该段通常需要的换乘次数
  - `crowding`：拥挤程度 1（清净）~ 5（非常拥挤）
  - 兼容旧权重列：`weight_meters` / `distanceMeters` / `weightMeters`；属性缺失时按距离推算步行耗时、其余按 0/1 处理

### 4.2 综合耗时权重模型
路径规划默认按“综合耗时”寻路（Dijkstra），单条边的折算公式：

```
综合耗时 = walk_minutes × (1 + 0.06 × slope_percent) × (1 + 0.06 × (crowding - 1)) + 10 × transfers
```

即：坡度每 1% 增加 6% 耗时、每级拥挤增加 6% 耗时、每次换乘惩罚 10 分钟（系数均可通过环境变量调整）。
同时用 Yen 算法求出综合耗时次优的若干条备选路线，与推荐路线一起返回，供前端对比解释。

### 4.3 容错策略
- 后端：`DataLoader` 对缺列/坏行进行跳过或给出明确的中文异常提示
- 前端：对节点 API 返回进行结构校验与清洗，避免脏数据触发运行时崩溃
- UI：ErrorBoundary 捕获不可预期异常并提示刷新重试

## 5. 性能与扩展
- 节点数量较小（景点级别）时，Dijkstra 在内存中运行即可满足交互性能
- 未来扩展点：
  - 引入真实道路网（大量边）时，可考虑启发式算法（A*）或预计算缓存
  - 支持用户自定义权重偏好（如“少换乘优先”“避开拥挤优先”）
